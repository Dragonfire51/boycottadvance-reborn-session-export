```c
/* ------------------------------------------------------------ joystick */
/* Joystick 0 is polled with WinMM's joyGetPosEx. The configured value per
 * keypad control is either a physical button number or a JOY_POV_*
 * sentinel; the four D-pad directions are matched against the hat angle
 * with a 45-degree acceptance cone. */
static int joy_read(int *buttons_out, int *pov_out) {
    JOYINFOEX ji;
    memset(&ji, 0, sizeof ji);
    ji.dwSize = sizeof ji;
    ji.dwFlags = JOY_RETURNALL;
    if (joyGetPosEx(JOYSTICKID1, &ji) != JOYERR_NOERROR) return 0;
    if (buttons_out) *buttons_out = (int)(ji.dwButtons & ((1u << JOY_MAX_BUTTONS) - 1u));
    if (pov_out) {
        if (ji.dwPOV == JOY_POVCENTERED) *pov_out = 0;
        else {
            int ang = (int)(ji.dwPOV / 100);          /* degrees 0..359 */
            int dir = 0;
            if (ang >= 315 || ang < 45)        dir = JOY_POV_UP;
            else if (ang >= 45 && ang < 135)   dir = JOY_POV_RIGHT;
            else if (ang >= 135 && ang < 225)  dir = JOY_POV_DOWN;
            else                               dir = JOY_POV_LEFT;
            *pov_out = dir;
        }
    }
    return 1;
}
```

```c
uint16_t ctl_joy_poll(const int *joymap) {
    uint16_t mask = 0x03FF;              /* nothing pressed */
    int buttons = 0, pov = 0;
```

## Hallazgo principal: deadlock circular en las escrituras diferidas de vídeo

El juego **sí** escribe `DISPSTAT`, pero no de forma directa. Su helper de E/S (`0x080010B4`) tiene este comportamiento:

- **Encola** la escritura en una tabla (`0x03000818`, lista de pendientes en `0x03000878`) **salvo que** se cumpla una de estas condiciones:
  - `DISPCNT & 0x80` (forced blank) está puesto, **o**
  - `VCOUNT` (`0x04000006`) está en la ventana de VBlank (comprueba el rango `0xA1..0xE0` = 161..224).
- La cola la vacía el **handler de VBlank del juego** (`0x08000788`, que llama a `0x0800103C`).

En un arranque en frío `VCOUNT`=0 y `DISPCNT`=0, así que la escritura de `DISPSTAT` queda **encolada y nunca se aplica**. Y como el bit 3 de `DISPSTAT` (habilitación de VBlank) nunca llega al registro, el handler que vaciaría la cola nunca corre → **deadlock circular**. Esto explica por qué `IE`=0005 y `IF`=0000 para siempre.

**Verificado**: forzando `DISPSTAT|=8` el juego aplica `DISPSTAT=0x9628` (pc `0x0800104E`/`0x08001058`) y el flag de espera `[0x030022DC]` pasa a 1.

## Segundo bloqueo (nuevo)

Con el bit 3 forzado el juego **ya no** se queda en `0x080008C6`, pero se cuelga en un bucle del **BIOS** en `0x00000120..0x00000124` (`str r0,[r4,r1]` / `adds r1,r1,#4` / `blt 0x120`) que no retorna (~2.4M hits por PC). Es un fallo **independiente**. Importante: el arranque con **BIOS real** (sin fastboot) también se cuelga exactamente ahí, así que es el bloqueador primario por resolver.

## ✅ OBJ Mosaic implementado según GBATEK — Publicado como v1.4.12

### Implementación (`src/ppu.c`, commit `37e2443`)
Siguiendo literalmente **GBATEK** ("Mosaic Function", sección OBJ) y contrastado contra el renderer software de **mGBA** (`software-obj.c` + `video-software.c`):

- **Activación**: por OBJ, `attr0` bit 12 (`Mosaic`).
- **Tamaños**: registro MOSAIC bits **8-11** = OBJ H-Size, bits **12-15** = OBJ V-Size (ambos −1).
- **Alineación a pantalla** (como mGBA): el bloque se engancha en `outX % mosaicH == 0` y `mosaicY = y - (y % mosaicV)`.
- **Color**: cada píxel es coloreado por el píxel superior-izquierdo del bloque (GBATEK).
- **Conteo vertical**: el bloque V se engancha por scanline y se **sujeta a las filas visibles del sprite** (`if (mos_y < ypos) mos_y = ypos; if (mos_y >= ypos+bh) mos_y = ypos+bh-1`) — exactamente el clamp de mGBA.
- **Affine OBJs**: el transform se muestrea en el origen del bloque (screen-aligned).
- Los mosaics **afs no-rotated** mantienen h/v-flip correcto.

## Qué encontré

El usuario pedía portar el modelo de bus de mGBA para resolver los glitches. **No era eso.** Al medir con método encontré tres cosas, en orden de impacto:

**1. El reloj del frame estaba mal (bug real, commit `56aa782`).** El frame debe durar exactamente 280.896 ciclos (228×1232), pero el nuestro avanzaba 285.776: **+1,7% por frame**. Causa: `run_frame_core` corría la CPU con presupuestos *relativos* (`arm_execute(g, 960)` / `272`); cada llamada se pasa del presupuesto al ejecutar la última instrucción y ese exceso se sumaba 456 veces por frame. Lo arreglé con límites **absolutos** por línea. Frames sin DMA salen exactos. mGBA reporta `frameCycles=280896`, lo que confirma el objetivo.

**2. La comparación era inválida (lo más importante).** Nuestro harness usaba `bios_fastboot = true` y lo comparaba con mGBA con `FASTBOOT=1`, que no es un arranque equivalente. Con **BIOS real en ambos lados**, Fire Emblem pasa de **19,86% a 1,08%** de divergencia. Y a frame 500 el estado del juego ya es casi idéntico a mGBA (VRAM 0,7%, EWRAM 0,1% de bytes distintos) pero renderizábamos 22% distinto: **solo era desfase de fase** en una animación que gira. Confirmado con los 4 bytes de IO que difieren a frame 30 (el juego ya escribió `WAITCNT` en nuestro run, vamos por delante; el BIOS deja `SIOCNT=0x6003` y el HLE no).

**3. El fastboot HLE era puro lastre.** Medido: mGBA enciende pantalla en el frame 7, nuestro HLE en el 0. Cambié el default a **BIOS real** (commit `2ed3c6a`), con fallback automático al HLE si falta el dump. La app ya trae `gba_bios.bin`, así que esto elimina los glitches visibles.

## Qué corregí

- `main.c`/`win32.c`: `BIOSFastBoot` default 0.
- `tools/headharness.c`: `NOFASTBOOT=1` y volcado `io.bin`.

### 1. Arreglo del audio "rayado" de DirectSound (la petición activa) — RESUELTO y publicado

**Causa raíz confirmada:** el Direct Sound (DAC de 8 bit relojado por Timer0 a ~13.4 kHz) se reproducía en **escalones** (sample-and-hold sin filtro): cada byte del FIFO se repetía tal cual durante N muestras de 44100 Hz. Eso inyecta ruido de alta frecuencia en cada transición — el "rayado".

**Arreglo** (`src/apu.c`, `apu_fifo_tick`): resampleo con **interpolación lineal**, igual que el resampler de mGBA. La fase avanza `STEP_FP/period` (16.16) por muestra de salida y se interpola entre las dos últimas muestras del FIFO (`fifo_prev`/`fifo_held`) → `fifo_interp`. El pop del FIFO y la petición DMA ocurren al cruzar la fase 1.0, o sea a la frecuencia exacta del timer. Eliminé `fifo_next` (era solo un reloj en ciclos de CPU para decidir el pop; ahora lo decide la fase).

More technical information:
Pokémon Emerald runs on the Game Boy Advance (GBA) hardware, which relies on a specialized, tile-based 2D graphics engine rather than modern framebuffers. Instead of rendering individual pixels on the fly, the GBA compose screens using grid-aligned graphics, hardware layers, and color palettes.
Here is a technical breakdown of how Pokémon Emerald brings Hoenn to life.

1. The GBA Video Modes and Background Layers

The GBA has several hardware video modes. Pokémon Emerald exclusively uses Mode 0, which is a pure text/tile mode.
• The Canvas: The GBA screen has a fixed resolution of 240 × 160 pixels.
• Four Background Layers (BG0–BG3): Mode 0 grants developers four independent, overlapping layers. Emerald uses them to manage visual depth:
	• BG0: Text boxes, menus, and the battle user interface (UI).
	• BG1 / BG2: The environment (buildings, trees, grass, water). By splitting the map across two layers, the game allows the player sprite to walk behind the tops of trees or roofs while staying on top of the grass.
	• BG3: Often used for distant backgrounds, like the shifting clouds during the title screen or battle backgrounds.

2. Tilemaps and VRAM

Because the GBA has very limited Video RAM (VRAM) and a slow CPU, it cannot store or render full image files. Instead, it uses Tile Mapping.
• The 8x8 Grid: Every environmental element is broken down into 8×8 pixel tiles.
• Tilesets: Graphics are compressed into a matrix of tiles stored in ROM. When you enter an area (like Route 104), the game loads the specific tileset for that environment into VRAM.
• The Map Matrix: The game world is built out of a grid of "metatiles" (usually 16x16 pixels, made of four 8x8 tiles). The game engine reads an array of numbers (e.g., Tile #45, Tile #46) and instructs the hardware to draw those specific tiles at specific coordinates.

3. Palettes and Color Management

The GBA handles colors using an indexed system to save memory, utilizing 15-bit RGB color (32,768 possible colors).
• Palette RAM (PRAM): Divided into two blocks of 256 colors each: 256 colors for backgrounds, and 256 colors for sprites.
• Sub-Palettes: These 256-color blocks are divided into 16 sub-palettes of 16 colors each (where Color 0 is always transparent).
• Dynamic Palette Swapping: Emerald achieves its dynamic environment transformations (like the day/night tinting or flashes of lightning) not by changing the images themselves, but by instantly rewriting the RGB values inside the PRAM.

4. Sprites and Objects (OAM)

Characters, Pokémon, projectiles, and moving water reflections are not part of the background tiles. They are handled by a dedicated hardware system called Object Attribute Memory (OAM).
• OAM Limits: The GBA can track a maximum of 128 sprites at once.
• Sprite Composition: Sprites can be sizes ranging from 8x8 up to 64x64 pixels. The player character sprite is typically composed of a 16x32 pixel block.
• Sprite Animation: To make a character look like they are walking, the CPU quickly swaps out the tile indices assigned to that sprite in OAM during the V-Blank (vertical blanking) interval of the screen refresh.

5. Advanced Engine Tricks in Emerald

Pokémon Emerald pushed the GBA hardware further than Ruby and Sapphire did, using clever software tricks:
• Sprite Animations: Emerald famously introduced animated battle sprites for Pokémon. Because VRAM is tight, the game dynamically streams new sprite frames into VRAM right before the animation plays and deletes them immediately after.
• Alpha Blending (Transparency): The GBA hardware supports blending two layers together. Emerald uses this for reflections in puddles, shadows on the ground, and the foggy overlay in the Mistralton-like areas or the Scorched Slab.
• H-Blank Effects: By changing the horizontal scroll register of a background layer on a line-by-line basis while the screen is drawing, Emerald creates the illusion of rushing, wavy water or heat distortion effects.

#define REG_BG0CNT      *(volatile unsigned short*)0x04000008
#define REG_BG0HOFS     *(volatile unsigned short*)0x04000010

#define MEM_VRAM        ((unsigned short*)0x06000000) // Video RAM

// Helper macros to navigate Charblocks (tilesets) and Screenblocks (tilemaps)
#define CHARBLOCK(n)    ((unsigned short*)(MEM_VRAM + ((n) * 0x4000))) 
#define SCREENBLOCK(n)  ((unsigned short*)(MEM_VRAM + ((n) * 0x400)))

    0x7C00, 0x7C1F, 0x7FFF, 0x2108

// Every 16-bit word contains 4 pixels (each pixel is a 4-bit palette index)

    0x1111, 0x1111, 0x1221, 0x1111,
    0x1221, 0x2222, 0x2332, 0x2222,
    0x2332, 0x3333, 0x3113, 0x3333,
    0x3113, 0x1111, 0x1111, 0x1111
};

void InitializeGBAEngine(void)
{
    // Step 1: Set the display to Mode 0 (Tile Mode) and activate Layer BG0
    REG_DISPCNT = MODE_0 | BG0_ENABLE;

    // Step 2: Configure BG0 settings
    // - Priority 0 (highest layer depth)
    // - Character Base Block = 0 (Load tileset to address 0x06000000)
    // - Screen Base Block = 30  (Load tilemap layout to 0x0600F000)
    // - Color mode = 0 (16-color mode / 4bpp)
    REG_BG0CNT = (0 << 0) | (0 << 2) | (30 << 8) | (0 << 13);

    // Step 3: Load the palette colors into Palette Memory
    for(int i = 0; i < 16; i++) {
        MEM_PALETTE_BG[i] = GrassTilePalette[i];
    }

    // Step 4: Write the physical Tile Pixel Matrix into Charblock 0
    unsigned short* tileSpace = CHARBLOCK(0);
    for(int i = 0; i < 16; i++) {
        tileSpace[i] = GrassTileData[i]; 
    }

    // Step 5: Construct the Map Layout in Screenblock 30 (32x32 grids)
    unsigned short* mapSpace = SCREENBLOCK(30);
    for(int y = 0; y < 32; y++) {
        for(int x = 0; x < 32; x++) {
            // Fill every coordinate of the map array with Tile Index #0
            mapSpace[y * 32 + x] = 0; 
        }
    }
}

La OAM (Object Attribute Memory) está físicamente dentro del chip de video de la GBA (el PPU / VDP), pero lógicamente mapeada en una dirección de memoria específica de la CPU para que puedas interactuar con ella.
Para entender exactamente dónde encaja y cómo se relaciona con los componentes que mencionas, aquí tienes el desglose técnico:

1. ¿Está en la PPU? Sí (Físicamente)

La OAM son 1 kilobyte de RAM interna dedicada que reside directamente dentro del procesador de gráficos de la GBA.
• El chip de video lee esta memoria constantemente en cada línea de escaneo para saber qué sprites (como el protagonista o un Pokémon) debe dibujar en la pantalla, en qué coordenadas (X, Y) y con qué colores.

2. ¿Dónde está en el mapa de memoria?

Para que el procesador (ARM/THUMB) pueda modificar la posición de los sprites, la OAM está mapeada en una dirección fija de la memoria del sistema: 0x07000000.
Si escribes datos en esa dirección, estás modificando directamente los registros de los sprites en la PPU.

3. ¿Qué relación tiene con el DMA? (El canal de comunicación)

El DMA (Direct Memory Access) no es donde vive la OAM, sino la herramienta que se usa para actualizarla de forma ultra rápida.
• La CPU de la GBA es demasiado lenta para mover los datos de los sprites uno a uno durante el renderizado sin causar parpadeos en la pantalla (sprite tearing).
• La estrategia de Pokémon Emerald: El juego crea una copia espejo de la OAM en la memoria RAM general del sistema (WRAM, usualmente en 0x03000000). Durante el juego, la CPU modifica tranquilamente ese espejo. Cuando la pantalla termina de dibujar un cuadro (durante el periodo llamado V-Blank), se activa el DMA Canal 3 para copiar instantáneamente esos 1024 bytes del espejo de la RAM a la OAM real (0x07000000) en apenas unos ciclos de reloj.

4. ¿Qué relación tiene con THUMB? (El set de instrucciones)

THUMB es simplemente el modo de ejecución de 16 bits del procesador principal (el ARM7TDMI de la GBA).
• Pokémon Emerald está compilado casi en su totalidad en modo THUMB para ahorrar espacio en el cartucho.
• El código THUMB es el que calcula las nuevas posiciones de los sprites (por ejemplo, X = X + 1 cuando caminas), pero guarda esos resultados en la RAM del sistema antes de que el DMA se encargue de enviarlos a la OAM en la PPU.

🎮 Hardware utilizado para las Gráficas (Mapeado en GBATEK)


1. LCD I/O Display Control (DISPCNT - 0x04000000)

• BG Mode 0 (Tile Mode): Pokémon se ejecuta exclusivamente en Mode 0. El motor gráfico lee mapas de baldosas de 8x8 píxeles en lugar de mapas de bits, optimizando el rendimiento.
• Screen Display (BG0 - BG3 y OBJ): Activa selectivamente las cuatro capas de fondo y la capa de sprites mediante los bits 8 al 12 de este registro.

2. LCD I/O BG Control (BG0CNT a BG3CNT)

• Character Base Block & Screen Base Block: Divide la VRAM (0x06000000). Especifica en qué bloque de memoria de video residen los "tilesets" (los dibujos de la hierba, casas, cuevas) y los "tilemaps" (la matriz que dice qué dibujo va en qué posición).

• Registros de Offset: Pokémon cambia estos registros en cada fotograma para mover la cámara por el mapa. Al modificar el desplazamiento horizontal y vertical mientras caminas, el hardware de la GBA desplaza los fondos sin consumir ciclos de CPU de cálculo de píxeles.

4. LCD OBJ - OAM Attributes (0x07000000)

• Attribute 0, 1 y 2: Controlan los sprites del jugador, NPCs y los Pokémon en combate.
	• Attr 0: Determina la posición Y, si el sprite está activo, y si usa paleta de 16 o 256 colores.
	• Attr 1: Determina la posición X y el tamaño del sprite (ej. 16x32 para el protagonista caminando).
	• Attr 2: Determina el "Character Name" (el número de baldosa inicial del sprite en VRAM) y su prioridad respecto a los fondos.

5. LCD I/O Color Special Effects (BLDCNT / BLDALPHA / BLDY)

• Alpha Blending (Modo 1): Utilizado para las transparencias de los reflejos del agua en los charcos de Ciudad Arborada o Ruta 120, mezclando las capas del mapa con el fondo inferior.
• Brightness (Modo 2 y 3 / BLDY): Emerald cambia el coeficiente de brillo de la pantalla en este registro para simular los relámpagos en la Ruta 119 o los fundidos a negro al entrar a un combate.

6. GBA DMA Transfers (DMA 3 - 0x040000D4)

• VRAM / OAM Updates: Pokémon utiliza el DMA Canal 3 durante el periodo de V-Blank (cuando la pantalla no está dibujando) para transferir a máxima velocidad datos gráficos descomprimidos desde la RAM al bloque de Sprites (OAM) o paletas.

1. GBA Sound Channel 2 - Tone (SOUND2CNT_L / SOUND2CNT_H)

2. GBA Sound Control Registers (SOUNDCNT_X - 0x04000084)

• Master Enable (Bit 7): Debe estar encendido para activar el reloj del sintetizador PSG de la consola.

=== 2. DISPCNT BIT 6 (OBJ VRAM MAPPING) ===
REG_DISPCNT 0x04000000: bit 6 = 0 → mapeo OBJ 2D; bit 6 = 1 → mapeo OBJ 1D. NO cachees este bit al arrancar: léelo al inicio de cada scanline (la evaluación de OBJ ocurre por línea).

=== 3. SONIDO CANAL 2 (onda cuadrada) ===
REG_SOUND2CNT_L 0x04000068:
- bits 0-5: longitud (counter = 64 - n, duración = (64-n)/256 s)
- bits 6-7: duty (0=12.5%, 1=25%, 2=50%, 3=75%)
- bits 8-10: paso de envelope (tiempo = n/64 s; n=0 → SIN envelope, volumen constante)
- bit 11: dirección (0 = decrece, 1 = crece)
- bits 12-15: volumen inicial (0-15)
REG_SOUND2CNT_H 0x0400006C:
- bits 0-10: frecuencia R. f = 131072 / (2048 - R) Hz. Periodo en muestras de duty = (2048 - R) pasos de 8 fases a 131072*8 Hz / ... usa un acumulador de fase de punto flotante/fijo, NO enteros truncados.
- bit 14: length flag (1 = el canal se apaga cuando el contador de longitud llega a 0; 0 = suena indefinidamente)
- bit 15: Initial (solo escritura, lee 0). Al escribir 1 → TRIGGER.

Lógica obligatoria:
1. TRIGGER (bit 15 = 1): channelEnabled = true; volume = (SOUND2CNT_L >> 12) & 0xF; envTimer = envStep; si lengthCounter == 0 → lengthCounter = 64; reinicia la fase del duty.
2. DAC: si (SOUND2CNT_L & 0xF800) == 0 (vol inicial 0 y dirección decrece) → DAC apagado → channelEnabled = false.
3. Frame sequencer a 512 Hz (cada 32768 ciclos de CPU a 16.78 MHz), 8 pasos, COMPARTIDO por los canales 1, 2 y 4:

4. Escribir longitud en bits 0-5 recarga lengthCounter = 64 - n SIN triggerear. El contador no corre si length flag = 0.
5. Salida: si !channelEnabled o volume == 0 → muestra 0 (silencio real, no el último valor). Cuando volume llega a 0 por envelope el canal se silencia pero NO es necesario deshabilitarlo.
6. Bit de estado en SOUNDCNT_X (0x04000084): bit 1 = canal 2 activo; se limpia al expirar la longitud.
7. SOUNDCNT_X bit 7 (master enable) = 0 → silencio y registros PSG no se escriben/pierden estado.
8. Mezcla: SOUNDCNT_L 0x04000080 (volumen maestro 0-7 por lado, bits 8-11 enable canales R, 12-15 L, canal 2 = bits 9 y 13), SOUNDCNT_H 0x04000082 bits 0-1 = escala PSG (0 = 25%, 1 = 50%, 2 = 100%).
